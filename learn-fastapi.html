01 · Orientation

The big picture

Before syntax, build the map. A FastAPI service is a pipeline: something arrives (HTTP), something decides (routing + dependencies), something works (your function), something persists (SQLAlchemy), something replies (Pydantic). If you can name the stage a bug lives in, you can fix it in minutes instead of hours.

Mental model

FastAPI gives you three seams and that's the whole framework: the route (URL → function), the schema (JSON ↔ Python objects), and dependencies (everything a handler needs, requested by type). SQLAlchemy gives you one more: the session (a unit of work that commits or rolls back). Master those four ideas and you can read any FastAPI codebase.

02 · Prerequisites

Python you need first

You don't need all of Python. You need about a dozen features, and this repo uses almost every one of them. Learn these and the framework code stops looking like magic.

Type hints — documentation the computer can check

Hints are not enforced by Python itself at runtime — but FastAPI reads them to build validation, docs and serialisation. list[Todo], dict[str, str], str | None (Python 3.10+ union syntax) are the three shapes you'll write most.

Annotated — attaching metadata to a type

Annotated[X, Y] means "X, plus fact Y". FastAPI reads Y for Path, Query, Body, Header and Depends. It's how you keep validation metadata next to the parameter instead of inside a default value — and it survives static type checkers, which x: UUID = Path(...) does not.

Generators and yield — functions that pause

Read it as "give the caller the session, keep my frame alive, finish the finally when they're done". FastAPI treats generator dependencies as setup/teardown: everything before yield runs before your handler, everything after runs after the response. This is the single most important Python feature for understanding request-scoped resources.

Context managers — with means "guaranteed cleanup"

Decorators — functions that wrap functions

@router.get/post/patch/delete registers your function in a lookup table and returns it unchanged. Nothing is "run" at import time except the registration. That's why a typo in a path shows up as a 404, not a crash.

Classes, __init__, and why ORM models look odd

raise ... from — keep the cause

You convert a library exception into an HTTP one — and chain it, so tracebacks still show the original cause. This is the standard translation pattern at the edge of your app. Note the deliberate opposite in main.py's health check, which uses from None to hide the underlying DB error from callers.

Project structure

The five rules this layout gets right

1. Models ≠ schemas

models.py is the database (persistence, relationships, constraints). schemas.py is the wire format (validation, JSON shape). Keeping them apart is what lets you add a DB column without leaking it to the API — and lets you refuse password_hash on the way out.

2. Routers are thin

A router file answers "which URL, which status code, which input/output shape". It should not contain the algorithm. auth.py owns token logic; routers/auth.py only wires it to paths. That's why the same rotation rules work for login and refresh.

3. Cross-cutting code lives once

get_current_user is used by nine routes. One place to add "check the account is active" later. Locality: fix once, fixed everywhere.

4. Tests mirror the app

routers/todos.py ↔ tests/test_todos.py. When you're unsure what a module does, its test file is the cheapest documentation available.

5. Config is one file, read once

No os.environ[...] sprinkled through routers. Everything typed, validated and cached in config.py. Missing variable = loud failure at startup, not at 3am on request 3,000.

Bonus: the app factory

create_app() returns a fresh application. Tests can build one with different settings; you can mount two in one process; nothing global is created at import time except the module-level app that uvicorn needs.

Where this layout drifts — and what to do about it

Template leftovers

This project started from a generic Python package template, and the skeleton is still visible: requirements.txt + requirements-dev.txt list Jupyter, tox, twine and mkdocs while uv.lock is the real dependency source; five GitHub workflows installs with pip install -e . on Python 3.11 while the project requires 3.13 and sets package = false; mkdocs.yaml points at someone else's repo and describes "a simple vector python package"; docs/index.md literally says "Fill out doc."

Lesson: a template is a starting point, not an architecture. Delete what you don't use. Two dependency manifests and three link tools is how a project ends up unbuildable after a rebase. Keep pyproject.toml + uv.lock; delete the rest.

When to add more folders

Don't pre-create layers. Add one when the pain is real, and add it in this order:

AddOnly whenPayoff
app/deps.pyTwo+ routers need the same composite dependencyOne alias like CurrentUser = Annotated[User, Depends(get_current_user)]
app/services/A rule is used by an HTTP route and a CLI job or webhookLogic survives without a request object
app/repositories/Queries get long, or you need two storage backendsQuery logic in one place, testable without HTTP
app/errors.pyYou repeat the same HTTPException shape 3+ timesConsistent error envelope
app/workers/Work must happen after the response (email, export)Background tasks, retries
Anti-pattern

Don't create utils.py, helpers.py, common.py, base_service.py, or an abstract BaseRepository with one implementation. Those become the drawer where unrelated things go to be forgotten. Name modules after the thing they own: tokens.py, passwords.py, todos.py.

04 · Framework

FastAPI core

FastAPI is five things bolted together: Starlette for HTTP, Pydantic for data, a dependency injector, a router table, and an OpenAPI generator. Learn those five and the framework is small.

The app factory and lifespan

Don't do this
# module-level engine: connects at import,
# breaks tests, leaks on reload
engine = create_engine(URL)

@app.on_event("startup")
async def start(): ...
Do this
# lifespan: explicit, testable,
# runs on TestClient enter/exit too
@asynccontextmanager
async def lifespan(app): ...

on_event("startup") is deprecated. Lifespan is the current API, and — crucially — it also runs inside TestClient(app), so your tests exercise the exact same setup and teardown path as production.

Routers: grouping URLs without a framework

prefix + path means POST /todos, not POST /todos/. Trailing slashes matter: "/todos" and "" cover the collection; use "/{todo_id}" for items. tags only affects the generated docs grouping — but it's what makes /docs pleasant, so use it.

response_model is a security feature

UserPublic sets model_config = ConfigDict(from_attributes=True), which is what tells Pydantic "read attributes off this ORM object, not dictionary keys". This is the modern replacement for the old orm_mode = True. Always set an explicit response_model on anything that returns a database object — it's your last line of defence against leaking fields, and it also generates accurate OpenAPI schemas.

Status codes and errors, done properly

Design decision worth copying

A todo that belongs to someone else returns 404, not 403. "Forbidden" would confirm the row exists — an information leak that lets an attacker enumerate IDs. The where-clause filters by user_id so ownership is enforced by the query itself, and the 404 is automatic. One helper, used by get, patch and delete: three routes, one rule.

Where validation lives: Pydantic schemas

field_validator vs model_validator

One field → @field_validator. A rule between fields → @model_validator(mode="after"). Raising ValueError from either becomes a clean 422 with a message; you never write that plumbing yourself.

One schema per intent, not per table

TodoCreate (input, required title) · TodoUpdate (all optional — PATCH semantics) · TodoPublic (output, includes server-generated fields). Reusing one model for all three is how you accidentally let clients set id or created_at.

PATCH means "only what's present"

# model_dump(exclude_unset=True) distinguishes
# "sent null" from "didn't send the field"
updates = body.model_dump(exclude_unset=True)

Validation is a trust boundary

Anything from a client is hostile until Pydantic has seen it. Constraints (min_length, max_length) belong here, not in an if inside the handler — they show up in the OpenAPI schema, so the front-end author can see them.

Sync or async handlers? The decision that trips everyone

def handler() (this repo)async def handler()
Runs ona worker thread (threadpool, ~40 by default)the event loop

Needsnothing extraasync driver (asyncpg), AsyncSession

The rule

Math is cheap, waiting is expensive. FastAPI runs sync handlers in a threadpool, which is fine and very common. But never mix: an async def handler that calls a blocking db.execute freezes the whole event loop. If you go async, go async everywhere (engine, session, driver) — don't half-migrate. The original design doc for this project specified async + PostgreSQL; it shipped sync + Snowflake, and that's a perfectly valid choice, but it means the handlers must stay def.

Templates and static files

Note parents[2] — __file__ is app/routers/pages.py, so parents[0]=routers/, [1]=app/, [2]=project root. Always resolve paths from __file__, never from the current working directory: uvicorn, pytest and a cron job all start from different cwds, and only one of them would be right.

The pages here are deliberately "dumb shells": Jinja renders HTML, then static/js/api.js does the API calls from the browser with the token in localStorage. That keeps one auth mechanism (Bearer tokens) instead of two (tokens + cookies), at the cost of the page flashing before JS runs.

Free stuff you get for free

/docs (Swagger UI), /redoc, and /openapi.json. Because your types are accurate, the generated schema is accurate — and other people's code generators, Postman, and LLM agents can all consume it. Keep it honest by always declaring response_model and never returning Response objects from typed routes.

05 · The killer feature

Dependency injection

If you learn only one FastAPI concept, learn this. Dependencies are how you declare "this handler needs X" and let the framework build X, cache it, and clean it up. Authentication, database sessions, pagination, feature flags and permissions are all the same mechanism.

Start with the smallest possible example

FastAPI inspects the signature, calls get_db, passes the yielded value, and runs the rest of the generator after the response is sent. The request has one session even if five dependencies ask for it — dependencies are cached per request by default (use_cache=True).

Dependencies form a graph

Here's the real chain in this repo. Read it bottom-up: each arrow is "needs".

Route → @router.get → get_current_user → {oauth2_scheme, get_db → app.state.session_factory}.

Two things make this elegant. First, a dependency can itself have dependencies, so handlers request exactly one thing (user) and get a verified identity. Second, validation happens before your handler body — a handler annotated with user: Annotated[User, Depends(get_current_user)] can never run unauthenticated. You can't forget the check, because forgetting it means the parameter doesn't exist.

What people get wrong

❌ Calling dependencies manually

# bypasses caching, needs a Request,
# re-implements the DI graph by hand
user = get_current_user(token, db)

Let the framework call it.

❌ Global mutable state

# two tests, two apps, same database
# handle → cross-contamination
CURRENT_USER = None

Pass values through the graph instead.

❌ Dependencies that raise in teardown

Exceptions after yield are raised while the response is being finalised — the client may already have a 200. Cleanup should swallow/log, not raise. This repo's finally: rollback(); close() is the right shape.

❌ Business logic inside a dependency

Dependencies are for acquiring and verifying context (who, which session, which page). "Create the todo" belongs in the handler or a service module. Keep the seam thin so you can test it.

Techniques worth knowing

Pattern 6 is the payoff

dependency_overrides is why DI exists. In a test you can authenticate as anyone with one line, fake an email provider, or pin the clock — without touching production code. If a test is painful to write, that's usually the signal that a value should have arrived as a dependency instead of being created inside the function.

06 · Persistence

SQLAlchemy 2.0

SQLAlchemy has four objects you must be able to tell apart: Engine (a connection pool), Session (a unit of work / transaction), Base (the mapping registry), and Model (a table). Confusing session with engine is the #1 beginner bug.

Setting it up

pool_pre_ping=True

Before handing you a pooled connection, SQLAlchemy pings it and discards dead ones. Essential for cloud databases and warehouses that silently close idle connections. It costs one cheap round-trip — far less than the mysterious "connection reset" it prevents.

expire_on_commit=False

By default, after commit() every attribute on your objects is expired — the next access triggers another SELECT. With False, objects keep their loaded values after commit, so the handler can return the object without a surprise query. That's why this repo still calls db.refresh(todo): to pull back server-generated values like created_at that Python never knew.

Declaring tables

Mapped[X] is not decoration — it decides the column's nullability and drives both static type-checking and Alembic's autogenerate. mapped_column() is the modern replacement for Column(). Know the difference between the two kinds of default:

These three columns in app/models.py are annotated as non-nullable but configured to be null: 

phone_number: Mapped[str] = mapped_column(String(20), unique=True, default=None)
full_name:    Mapped[str] = mapped_column(String(255), default=None)
age:          Mapped[int] = mapped_column(Integer, default=None, nullable=True)

Mapped[str] means NOT NULL. default=None is not a default — it means "no default at all". The migrations created these columns as nullable, so it works today only because INSERTs omit them. Run alembic revision --autogenerate and it will happily generate SET NOT NULL on columns full of NULLs. The fix is one character: Mapped[str | None].

Querying: the 2.0 style

Use scalar_one_or_none() when you're fetching one row by primary key or a unique column — if it ever returns many, your constraint is broken and you want to know. Use first() only when duplicates are legitimate and you're ordering deliberately.

Never build SQL with f-strings. select(Todo).where(Todo.id == value) sends value as a bound parameter, so injection is structurally impossible. The legacy db.query(Todo).filter(...) API still works, but 2.0's select() is what you should learn — it composes better and matches the docs.

The unit of work: commit, refresh, rollback

Why rollback in finally, when handlers already commit?

Because rollback() on a session with nothing pending is a no-op, while a session left dirty by an exception holds a transaction and locks. The dependency guarantees one clean ending for every outcome — 200, 404, 500, or a client that hung up. Cheap insurance: sessions must never leak, transactions must never stay open.

Ownership, N+1, and pagination

N+1: one query per row
todos = db.execute(select(Todo)).scalars().all()
for t in todos:
    print(t.owner.username)  # SELECT per todo!
Two queries total
from sqlalchemy.orm import selectinload

stmt = select(Todo).options(selectinload(Todo.owner))
todos = db.execute(stmt).scalars().all()

N+1 is invisible on 3 rows and fatal on 3,000. Rule of thumb: if you loop over objects and touch a relationship inside the loop, you need eager loading (selectinload for collections, joinedload for many-to-one).

This repo returns all of a user's todos with no limit. Fine for a demo; a real API needs limit/offset (or a cursor) plus a stable sort key. Note the tie-break on id: without it, two todos created in the same timestamp can swap places between requests, and clients see duplicates or gaps while paging.

07 · Schema history

Migrations with Alembic

Your models describe what the schema should be. Migrations are the ordered, reviewable steps that get a real database there — and, crucially, the only record of what production currently looks like.

Autogenerate is a draft, not an answer

A migration you can read

down_revision is the parent pointer — that's the whole "chain". Two migrations with the same down_revision create a branch, which is why alembic upgrade head suddenly complains after two people merge schema changes on different branches.

Rules that save you at 2am

Always write downgrade()

Autogenerate often leaves it empty. An irreversible migration can't be rolled back when the deploy goes wrong — you get to write a forward fix under pressure instead.

Never edit an applied migration

Once it's on someone else's database, editing it does nothing there and creates drift everywhere. Add a new revision instead — the history is append-only.

Separate schema from data

Adding a NOT NULL column to a table with rows fails. The safe sequence is: add nullable → backfill in a data migration → enforce NOT NULL in a third revision. Three boring steps beat one outage.

Run migrations as a deploy step

Not on app start (two replicas race), not manually on prod at midnight. One explicit command before the new code goes live — Render's pre-deploy hook, or a CI job.

Check in env.py

It's part of your app. Here it does something clever: Snowflake has no built-in Alembic DDL dialect, so alembic/env.py registers a minimal one (SnowflakeImpl) — otherwise every migration crashes with an unknown dialect.

Tests should tell you when models drift

Cheap habit: in CI, run alembic upgrade head on an empty database, then alembic check (or autogenerate into a temp file) and fail if it produces operations. That catches "someone changed a model and forgot the migration" automatically.

08 · Security

Auth & JWT

Authentication is where beginners ship vulnerabilities, because everything "works" while being wrong. This section walks the real implementation and names the traps.

Passwords: hash, never store

DoDon't
Argon2id (or bcrypt) via a maintained library (pwdlib)SHA-256/MD5, or rolling your own
Let the library pick parameters; re-hash on login when they changeHardcoding iteration counts from a 2015 blog post

verify_password is constant-time inside the library: it doesn't early-return on the first mismatched byte. That's why you use a library and don't compare hashes with == yourself.

What's inside a JWT

A JWT is three base64url chunks joined by dots: header.payload.signature. The payload is signed, not encrypted — anyone can read it. Paste a token into jwt.io and you'll see this app's claims immediately:

Never put secrets in a JWT

No passwords, no credit cards, no internal role lists you wouldn't show the user. Signing prevents tampering, not reading. Roles in a token are also stale by design — a revoked admin keeps admin until the token expires. Keep access tokens short-lived for exactly that reason.

Rotation: the part that makes refresh tokens safe

Why each check exists:

Check 2 — the type claim

Without it, a 7-day refresh token is a valid access token: same signature, same secret. This repo has a test for exactly that (test_refresh_token_rejected_as_access) — a leak of the refresh token would otherwise grant permanent API access.

Checks 4 & 6 — hashed, revocable, single-use

The DB stores sha256(token), so a database leak doesn't hand over working tokens (you can't reverse a hash). On refresh, the old row is marked revoked_at and a new pair is issued — so a stolen refresh token that gets used invalidates itself for the legitimate user, which is how you detect theft.

Check 5 — server-side expiry is the real one

Never trust the client's clock or the token's exp alone. Both are checked: JWT expiry for cheap rejection, DB expires_at as the authority.

Check 3 — an allowlist, not a denylist

A token is valid only if a row exists. This is what makes logout and "revoke all sessions" possible at all. Stateless JWT purists sometimes skip the table; then you can never log anyone out, and you'll add it back later under pressure.

Note the two secrets doing two jobs: hash_refresh_token (SHA-256) is a lookup — fast, one-way, fine because the token is already high-entropy. hash_password (Argon2) is slow on purpose because human passwords are guessable. Don't swap them.

This project gets 1–5 right, and trips over 6 in routers/user.py: reset_password changes the hash but leaves every refresh token alive, so a previously stolen refresh token still mints new access tokens after the victim changes their password. Section 11 has the fix.

The client side of auth

Notice what this app does not do: it never calls /auth/refresh automatically. With a 90-second access token (or even 15 minutes), users get bounced to the login page mid-session. The production pattern is a single retry: on 401, try one refresh (deduplicated across concurrent requests), then replay the original request; only redirect if the refresh also fails. That's a good exercise — see section 15.

09 · Confidence

Testing

Tests are how you change code without fear. For a web API, the cheapest high-value tests hit HTTP routes — the same seam your users cross. This repo does that, and it's the right call at this size.

The fixture that makes it all possible

Three lessons in six lines. (1) TestClient used as a context manager runs the lifespan, so tests exercise the real startup path. (2) create_app() per test means no cross-test leakage through a global app. (3) get_settings.cache_clear() is what makes lru_cache'd settings testable — memoisation and test isolation fight each other, and this is the standard reconciliation.

What a good route test looks like

This is the single most valuable test in the repo: it asserts a security property (users can't read each other's data) across every verb, not just the happy path. Test the shape of the action you fear, not the one you're proud of.

The trap in this suite

tests/conftest.py auto-skips every test when SNOWFLAKE_ACCOUNT is unset:

Locally that's friendly. In CI it means a green pipeline that ran zero assertions — the most dangerous kind of green. 10 · Environment

Config & secrets

The twelve-factor rule: configuration lives in the environment, not the code. This repo does it well — one typed settings object, read once, validated at startup.

Why required fields have no default

A missing SECRET_KEY should crash on boot with a readable Pydantic error, not produce tokens signed with None at runtime. Fail at startup, loudly, once.

Why lru_cache

Reading and parsing .env on every request is waste; parsing it once means a single validated config object. The cost: tests must call get_settings.cache_clear() — which is exactly what conftest.py does.

The URL builder isn't paranoia

Passwords with @, : or / break hand-assembled connection strings. snowflake.sqlalchemy.URL(**kwargs) escapes correctly, and it keeps the credentials out of a single long string you'd be tempted to log.

extra="ignore"

Tolerates unrelated variables in the environment (CI, PaaS, shells). The stricter extra="forbid" is useful when typos in variable names are a real risk: it turns SECRET_KEYS=… into a startup error instead of a mystery.

Secrets in the repo
# .env committed, or hardcoded
SECRET_KEY = "dev-secret"
DATABASE = "user:pw@host/db"
# → rotate EVERYTHING after the leak
Secrets in the environment
.env          # gitignored ✔
.env.example  # committed, fake values, documents keys ✔
# prod: the platform's secret store

This repo does exactly this, and .env is genuinely ignored (git check-ignore .env confirms it) — worth verifying in your own projects, because a file that appears in ls feels committed even when it isn't.

The drift you should design against

app/config.py defaults the access token to 90 seconds (with a # was 900 comment), while .env.example and the README both say 900. Locally the value comes from .env; in the tests it comes from nothing at all; in production from the platform's dashboard. Three sources of truth for one number is a bug waiting for a support ticket. Pick one: either the durable default in config.py is the documented value everywhere, or the setting is required with no default and every environment must state it.

11 · Practice

Audit: bugs in this repo

Reading code critically is the fastest skill to build. Below are twelve real findings from this codebase, ordered by how much damage they cause. Try each one first — the ✦ reveal has the reasoning and the fix. Being able to spot these in someone else's PR is what "senior" means.

Ground rules for a code review

Ask three questions of every line: Is it correct? (all inputs, not just the happy one) · Is it safe? (trust boundaries, secrets, authorization) · Will the next person understand it? Report what you verified, not what you suspect — and say why it matters, because "this is wrong" without impact gets ignored.

Findings

Severity: high · security

1. Changing your password doesn't log anyone out

PATCH /user/reset-password in app/routers/user.py updates user.password_hash and commits. Nothing touches refresh_tokens. Why does that matter?

✦ reveal: impact + fix

Refresh tokens are bearer credentials with a 7-day life. If an attacker stole a refresh token (stolen laptop, leaked log, XSS), the victim's password change does nothing: the attacker keeps calling /auth/refresh and minting fresh access tokens. The whole point of a password reset is regaining control of the account.

There's a second-order issue too: rotating a refresh token revokes only that token, so a stolen one is revoked only if the thief uses it after the legitimate client. The robust pattern is token families — when a revoked token is presented, revoke every token in the same family — plus a global kill switch.

Test to write with it: log in twice (two refresh tokens) → reset password → both tokens must return 401.

Severity: high · correctness

2. Only one white-space strip? No — it's the type annotation that lies

app/models.py declares nullable columns as non-nullable. Look at phone_number, full_name, age. What breaks?

✦ reveal: impact + fix

Mapped[str] means NOT NULL in SQLAlchemy 2.0's type map. default=None is not a default — it's "no default", so the INSERT simply omits the column and relies on the database's nullability (which the migrations set to nullable). So the code works today and lies to every tool that reads it:

→ alembic revision --autogenerate will emit ALTER TABLE users ALTER COLUMN full_name SET NOT NULL, which fails on any table containing a NULL. → static checkers treat user.full_name as str, so UserPublic.full_name: str | None looks like a contradiction. → the next dev writes user.full_name.upper() and gets an AttributeError for users with no name.

Note the last one: nullable=True was only needed because the annotation said non-nullable. The annotation is the single source of truth — fix the annotation and the override disappears.

Severity: medium · race condition

3. The duplicate-username check is a time-of-check/time-of-use race

app/routers/auth.py, register(). Two requests with the same username arrive at the same moment. What happens?

✦ reveal: impact + fix

Both run SELECT … WHERE username = 'alice', both see nothing, both INSERT. On Snowflake that's two rows with the same username unless the unique constraint is enforced (it is, per the model and migration) — in which case one INSERT raises IntegrityError, which the app doesn't catch: the user gets a 500 instead of a clean 409, and the session is left in a failed state.

The lesson generalises: a pre-check SELECT is a UX nicety, never a guarantee. The database constraint is the guarantee; your job is to translate its failure into the right HTTP status.

Keep the SELECT if you want the friendly message in the common case, but the try/except is the part that must exist. Note db.rollback(): after an IntegrityError the session is unusable until it's rolled back.

Severity: medium · inconsistency

4. Register accepts a 1-character password; reset demands 10

UserCreate.password: str = Field(min_length=1) vs ResetPasswordRequest.new_password: str = Field(min_length=10). Spot the problem, and the deeper one.

✦ reveal: impact + fix

The obvious bug: you can register with "a" but can never set that same password through the reset endpoint. Any user who registered with a short password is stuck — the "reset" would reject their existing choice, and there's no "current password" check at all.

The deeper issue: a password policy is one rule, written twice, in two files. That's how policies diverge. Extract it:

Also worth noting: max_length matters. Argon2 on a 10 MB password is a free denial-of-service, and hashing cost scales with input length.

Severity: medium · testability

5. get_db reaches into app.state instead of receiving what it needs

session = request.app.state.session_factory(). It works. What does it cost?

✦ reveal: the trade-off

It couples the dependency to the whole application object, which is why tests/test_db.py has to build a fake SimpleNamespace(app=SimpleNamespace(state=…)) and mock a session — a test that verifies a mock was called, not that sessions are managed correctly. That's a smell: the test is testing past the interface.

The fix is the standard FastAPI pattern — make the factory itself a dependency, so it can be overridden in tests without any request object:

Now a test can do app.dependency_overrides[get_session_factory] = lambda: fake_factory and assert real behaviour. This is the "accept dependencies, don't create them" rule: a function that receives its collaborators is testable; one that digs them out of a global is not.

Severity: medium · operations

6. Login has no rate limit, lockout, or delay

POST /auth/login verifies a password for every request, forever.

✦ reveal: impact + pragmatic fix

Argon2 is deliberately slow — that's a feature against offline cracking, and an amplification vector against you: an attacker can spend one cheap HTTP request to make your server burn ~50 ms of CPU. Parallel bots also get unlimited guesses at weak passwords.

Minimum viable defences, cheapest first: (1) per-IP and per-username counters in the database or a cache with an exponential backoff, (2) return 429 with Retry-After, (3) log and alert on spikes. Redis is the usual home for this, but a table with an index is fine at small scale — don't add infrastructure before you need it.

Severity: medium · engineering hygiene

7. CI is green and has never run a single test

tests/conftest.py skips everything without SNOWFLAKE_ACCOUNT, and .github/workflows/test.yaml never sets it.

✦ reveal: impact + fix

The most expensive failure mode in software: false confidence. Nobody notices the skipped tests because the checkmark is green. Meanwhile the workflow has other problems — Python 3.11 (project needs 3.13), pip install -e . (project sets package = false), a duplicated Windows job, requirements-dev.txt instead of uv sync.

The real fix is to make CI self-sufficient: run against a throwaway Postgres service container so no credentials are needed.

That last step is the cheap guard: if the count is zero, fail loudly. (Doing it properly means making the database configurable — this repo hardcodes Snowflake in config.py, so a DATABASE_URL override is itself a small refactor worth doing.)

Severity: low · dead code

8. A column no API can ever write, and fields that can never be cleared

users.phone_number exists in the model, the migration and UserPublic. UserUpdate has only full_name and age.

✦ reveal: the lesson

phone_number is read-only forever: UserPublic returns it, nothing sets it. All three layers pay for it (column, schema, response payload) and the feature doesn't exist. Meanwhile UserUpdate's None means "not provided", so a user can never clear their full name or age — write-once fields, which is why update_profile has those two if … is not None guards.

The generalisable rule: in a PATCH, None is ambiguous. Either use a sentinel (model_dump(exclude_unset=True) plus Field(default=None), and treat explicit null as "clear"), or accept "" as the clearing value and document it. Decide deliberately; don't let it fall out of the type system.

Severity: low · robustness

9. /health catches Exception and hides the reason

Deliberate — but is it the right kind of deliberate?

✦ reveal: the nuance

Fetching from a warehouse can fail for many reasons (warehouse suspended, network, bad password). Mapping all of them to "503 database unavailable" is defensible for a load balancer probe: it should not leak connection strings or credentials to anonymous callers. The from None is the deliberate part.

What's missing is the other half: log the exception server-side before swallowing it. Otherwise the operator sees "database unavailable" and has no way to tell "Snowflake password rotated" from "warehouse asleep" — and the first one is a 5-minute fix while the second is a 5-second wait.

Severity: low · data lifecycle

10. refresh_tokens grows forever

Every login and every rotation adds a row. Nothing ever deletes one.

✦ reveal: impact + fix

In a warehouse, storage is cheap but scans aren't: the table grows without bound, so the index that jti lookups rely on gets slower (and every query you write against it later has to remember to filter). Expired rows are pure debt — a revoked token can never become valid again.

A retention job, run daily, is the whole fix:

Thirty days past expiry is a deliberately generous margin: it lets you investigate a suspicious session after the fact. Keep the audit trail you actually use, delete the rest.

Severity: low · docs drift

11. Three sources of truth for two numbers, and a spec describing a different app

The token TTL (90 vs 900), the missing PATCH /user/profile in the README's API table, an empty docs/api.md, and a design spec that says async Postgres + Docker Compose while the code is sync Snowflake with no Dockerfile.

✦ reveal: why this is a real finding, not nitpicking

Stale docs are worse than missing docs, because people act on them. The concrete harm here: a new contributor reads the spec, writes async tests against Postgres, and burns a day on a mismatch that no code comment explains.

Two habits fix this class of problem permanently: (1) one source of truth per fact — if .env.example is the contract, config.py shouldn't carry a competing default, or vice versa; (2) date and status your specs — "2026-09-15, superseded by app/ (sync Snowflake)" takes ten seconds and saves the reader a day. Put the historical plan in a docs/adr/ or delete it; don't leave it looking current.

Severity: low · UX

12. Every 90 seconds the user gets kicked to the login page

The access token expires quickly; api.js reacts to any 401 by clearing tokens and redirecting. The refresh token is never used by the client.

✦ reveal: the fix pattern

With a 90-second access token, a user who reads a page for two minutes and clicks "Add" is logged out. The refresh token exists precisely to prevent this — the client just has to use it. The correct pattern is a single-flight refresh-and-replay:

Two subtleties that trip people up: the shared promise matters (ten parallel 401s must trigger one refresh — rotation means the second refresh would use an already-revoked token and log everyone out), and if multiple tabs are open, the second tab holds a stale refresh token and will fail. Production apps listen for a storage event to sync tokens across tabs.

What this repo gets right (copy these)

Ownership enforced in the query with 404-not-403 · hashed refresh tokens with rotation and a type claim · a single deep auth.py instead of auth logic in nine routes · response_model everywhere so nothing leaks · lifespan-managed engine with pool_pre_ping · session teardown in finally · settings validated at startup · .env gitignored with a documented .env.example · a test that asserts a security property across every verb.

Clean-code playbook

Clean code isn't aesthetics — it's the cost of the next change. Every rule below exists because violating it has a measurable price: a bug that ships, or an hour somebody spends confused.

Functions: small, and doing one thing

A good function is one you can describe without "and". Look at what this repo does well: decode_token decodes, get_refresh_row validates and returns the row, issue_token_pair creates and persists. Each is testable in isolation, each has one reason to change.

One function, five jobs

    # check revocation, load user, revoke old,

Composed of named steps
def refresh(body, db):
    row = get_refresh_row(db, body.refresh_token)
    row.revoked_at = datetime.now(UTC)
    user = db.get(User, row.user_id)
    if user is None: raise HTTPException(401, …)
    tokens = issue_token_pair(db, user)
    db.commit()
    return tokens

Notice that the "good" version is only ten lines, and each line names a concept. That's depth: the handler reads like a summary, and the detail lives behind interfaces that are tested once.

Error handling rules

Translate at the edge

Library errors (jwt.PyJWTError, IntegrityError) become HTTP errors exactly once, where the request meets your code. raise … from exc keeps the cause for the logs.

Never except: pass

Silently swallowing an error converts a loud bug into an inexplicable one. If you must catch broadly, log it — see finding 9.

Catch the narrowest type

except jwt.PyJWTError won't hide a typo'd variable name; except Exception will. Broad catches belong only at boundaries (a health probe, a worker loop, a top-level handler).

Fail loudly at startup

Missing config, unreachable migrations, an unimportable router — all should stop the process. A service that boots with broken configuration fails at the worst possible moment.

Comments: explain why, or delete them

The # was 900 comment in config.py is the interesting one: it's a real signal that someone made a deliberate change, but it records that fact in the worst place. The right home is the commit message ("drop access TTL to 90s for demoing refresh flows"), which git log -p will surface forever without cluttering the code.

Tooling: one formatter, one linter, one source of truth

pyproject.toml here configures ruff + black + isort + mypy + pyright simultaneously, with rules that disagree (ruff format vs black, ruff's I rules vs isort, mypy's Python 3.10 vs the project's 3.13). The pre-commit config then pins two different ruff versions (v0.2.1 for format, v0.2.0 for lint) and runs mypy over . including the excluded directories.

Commits and reviews

Small, thematic commits

One idea per commit; the message should let a reader reconstruct why. Compare "add full_name and age to users" (model + migration + schema + test) with a 400-line "updates". The first is reviewable and revertable; the second is a hostage situation.

Review your own diff first

git diff before git commit catches: leftover debug prints, commented code, an accidental .env, a 2000-line lockfile change with three real lines. Sixty seconds, saves a round-trip.

Test the new behaviour, not the implementation

If a refactor with identical behaviour breaks your tests, they were testing the wrong thing. This repo's route-level tests survive any internal reshuffle — that's the goal.

Comments in review > comments in code

"Why did you suspend the 90s TTL here?" on the PR is the right place for that discussion. The code keeps the decision; the PR keeps the reasoning; git blame connects them.

The two habits that upgrade code quality fastest

1. Make the change easy, then make the easy change. If a feature feels hard to add, the structure is telling you something — do the refactor first, in its own commit, while tests are green. 2. Delete code. Every line you remove is a line nobody has to read, test, migrate, or debug. The requirements.txt, the extra workflows, the unused column: deleting them is the improvement.

Order of operations on every deploy

Migrations first, then new code. Write migrations so they work with both versions of the app (add a nullable column; don't rename in one step). If you deploy code first, requests hit a schema that doesn't exist yet. If you ever need to roll back code, the additive migration stays — that's why expand/contract beats a single destructive rename.

Observability: the minimum viable version

Logs that answer "what happened?"

Log at boundaries: request received (path + user id, never tokens), auth failures, unexpected exceptions with logger.exception, and slow queries. Never log passwords, tokens, or connection strings — a leaked log is a leaked credential.

A request id

Generate one per request in middleware, return it in a header, include it in every log line. When a user reports a bug you can find their request in a sea of logs. This is the single highest-value observability addition to any API.

Metrics worth having first

Request count + latency by route and status; auth failure rate; DB error rate. Four numbers give you 90% of incident diagnosis. Add tracing later, when you have services talking to each other.

Alerts that fire on symptoms

Alert on user-visible symptoms (error rate, p95 latency, health check failing twice), not on causes (CPU 60%). An alert nobody acts on gets muted, and then you have no alerts.

Secrets hygiene, since this app has real ones

SECRET_KEY is the master key: whoever has it can mint tokens for any user. Rotate it by running two keys (sign with the new, verify against both) so sessions survive. Same for the Snowflake password: put it in the platform's secret store, scope the role to the minimum (not ACCOUNTADMIN as in .env.example — that's a demo placeholder and a genuinely dangerous default), and know that rotating it once is a one-line dashboard change.

Exercises

Reading builds familiarity; typing builds skill. Do them in order — exercise 1 is the whole vertical slice, and 2–12 each target one concept. Every one is small enough for an evening.

01 · the full vertical slice · ~2h

Add a due_date to todos, all the way through

The single most useful exercise in this list: it touches every layer, so you learn the order of the work. Do it in this sequence and don't skip steps.

  1. models.py: due_date: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
  2. uv run alembic revision --autogenerate -m "add due_date to todos" — then read and fix the generated file
  3. uv run alembic upgrade head, then downgrade -1, then upgrade head again (prove it reverses)
  4. schemas.py: add the field to TodoCreate, TodoUpdate and TodoPublic — note which ones need | None
  5. templates/app.html + static/js: a date input and a display of the value
  6. tests/test_todos.py: create with a due date, assert it round-trips, assert a foreign user can't see it
✦ reveal: gotchas you'll hit

A. Autogenerate will also try to "fix" the nullable annotations from finding 2 — review the diff and delete unrelated operations. B. Dates arrive as ISO strings; <input type="date"> gives you "2026-10-01", which Pydantic parses into a datetime at midnight in UTC — decide whether you want a date or an instant, and be explicit. C. Timezones: store aware datetimes, render in the browser with toLocaleDateString(). D. Existing rows are NULL, so make it optional in the schema from day one — that's the expand step of expand/contract.

02 · security · ~20min

Make a password reset end every session

Implement finding 1, then write the test: two logins → reset password → both refresh tokens must 401.

✦ reveal: expected shape

A single update(RefreshToken).where(user_id == …, revoked_at.is_(None)) in the same transaction as the password change, plus a test that proves it. Bonus: also assert that new logins after the reset still work, so you didn't over-revoke.

03 · unit testing · ~30min

Test the token helpers directly — no HTTP, no database

create_access_token, create_refresh_token, decode_token, hash_refresh_token are pure functions. They're the cheapest tests in the codebase and currently untested.

✦ reveal: the assertions worth making 
def test_access_token_claims():
    token = create_access_token("user-123")
    payload = decode_token(token)
    assert payload["sub"] == "user-123"
    assert payload["type"] == "access"
    assert payload["exp"] > payload["iat"]

def test_tampered_token_rejected():
    token = create_access_token("user-123")
    with pytest.raises(HTTPException): decode_token(token[:-2] + "xy")

def test_refresh_hash_is_stable_and_not_the_token():
    token, _ = create_refresh_token("u")
    assert hash_refresh_token(token) == hash_refresh_token(token)
    assert token not in hash_refresh_token(token)
04 · expiry · ~30min

Prove that an expired token is rejected

You can't wait 90 seconds in a test suite. Make time injectable — either freeze it (freezegun / time-machine) or build the token with an exp in the past.

✦ reveal: the trick

Simplest version: call create_access_token, decode it without verification (jwt.decode(token, options={"verify_signature": False})), then re-encode the same claims with exp = now - 1s and the real secret. Now you have a genuinely expired, correctly signed token. Assert 401 from /user/me. This teaches you that a JWT is just data plus a signature — which is why the type claim matters.

05 · pagination · ~1h

Paginate GET /todos without breaking the tests

Add limit (1–100, default 20) and offset (≥0), with a stable sort, and return the total count so a client can render page numbers.

✦ reveal: design questions to answer

Where does the default live — in the signature or in the schema? Should the response be a bare list (breaking existing clients) or an envelope ({"items": [...], "total": 42})? Which is the tie-break column, and why does an unstable sort produce duplicates while paging? How would cursor pagination (?after=<created_at,id>) avoid the offset drift that happens when rows are inserted mid-scroll? There's no single right answer; there is a right reasoning, and it's worth writing down.

06 · structure · ~1h

Extract a Todos service — then argue about whether you should have

Move the ownership query and the create/update logic out of the router into app/services/todos.py, returning domain objects and raising domain errors that the router translates into HTTP.

✦ reveal: the honest evaluation

You gain: logic testable without HTTP; a seam for background jobs; the router becomes a one-line-per-route translation layer. You lose: a layer of indirection, and now every change touches two files.

Verdict for this codebase: probably not worth it yet — the logic is two lines and used once. Add the layer when a second caller appears (a CLI, a webhook, an admin panel), because one adapter means a hypothetical seam. Being able to make this argument, with the costs named, is the real skill.

07 · frontend · ~1.5h

Refresh-and-replay in api.js

Implement finding 12: on 401, refresh once, replay once, redirect only if the refresh fails.

✦ reveal: how to know you got it right

Open the app, wait for the access token to expire, click "Add". It should work silently, and the Network tab should show: POST /todos → 401, POST /auth/refresh → 200, POST /todos → 201. Then break it deliberately: revoke the refresh token (log out in another tab) and confirm the app redirects instead of looping forever. A retry loop with no exit is the classic bug here — always limit yourself to one replay.

08 · infrastructure · ~1.5h

Make the test suite runnable without Snowflake

Accept a DATABASE_URL override in config.py, point the suite at a throwaway Postgres, and make CI fail if zero tests run.

✦ reveal: the plan

Add database_url: str | None = None to Settings and have sqlalchemy_url() return it when set. Run Postgres in Docker or as a CI service container. Then decide the hard part: you're now maintaining two dialects, so a Snowflake-only feature (or an Alembic DDL quirk) could pass in CI and fail in prod — which is exactly why the original design said "test against the real thing". Note the trade-off explicitly in the README; that's what a senior engineer does instead of pretending it's free.

09 · database · ~45min

Find and index the slow query

GET /todos filters by user_id and sorts by created_at desc. What index would make that a single range scan? Write the migration.

✦ reveal: answer

A composite index on (user_id, created_at DESC). A single-column index on user_id (which this repo has) narrows the rows but still requires a sort. The composite one satisfies both the filter and the order, so the database can walk the index directly. Bonus: measure before and after with EXPLAIN — an index you didn't measure is a guess, and indexes cost writes and storage.

10 · hardening · ~1h

Rate-limit login

Implement finding 6 with a DB table (username, window_start, failures), then test it: 10 bad attempts → 11th returns 429 with Retry-After.

✦ reveal: details that matter

Count failures, not requests, and reset the window on success (otherwise a valid user gets locked out by their own typo). Key on both username and IP — keying only on username lets an attacker lock out a victim; keying only on IP punishes everyone behind one NAT. Return the same generic error message whether or not the account exists, or you've built an oracle while trying to prevent brute force.

11 · docs · ~30min

Kill the drift

Fix finding 11: make the TTL match everywhere, document PATCH /user/profile, delete the dead template scaffolding (requirements*.txt, unused workflows, the mkdocs config, docs/index.md), and mark the old spec as superseded with a date.

✦ reveal: why this is worth an evening

It's the highest ratio of "hours saved for the next person" to "hours spent" in the whole list, and it's the work nobody volunteers for. Deleting 200 lines of unused config also removes 200 lines of future confusion — that's why "delete code" is the first habit in section 12.

12 · ambitious · a weekend

Port the whole app to async PostgreSQL

The path the original spec intended: asyncpg + create_async_engine + AsyncSession + async def handlers, tests against Postgres.

✦ reveal: what you'll learn the hard way

Every db.execute needs await. Lazy loading raises MissingGreenlet — async SQLAlchemy forbids implicit I/O, so you must eager load deliberately (that's a feature: it makes N+1 bugs loud). Your dependency becomes an async generator. TestClient works, but lifespan and engine disposal change shape. When you're done you'll understand exactly why "sync or async" is a whole-application decision, not a per-file one — which is the real lesson.

The three sentences to remember

1. FastAPI is routes + schemas + dependencies; SQLAlchemy is one engine, one session per request, one unit of work. 2.
